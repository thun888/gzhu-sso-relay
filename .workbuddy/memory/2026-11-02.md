# 2026-11-02

## 用户中心注销账号与统一邮件确认层

- 新增 `internal/confirm`：通用 Redis 令牌存储，按 `Kind`（`email` / `account`）隔离，键为 `relay:confirm:<kind>:token:` 与 `relay:confirm:<kind>:user:`，TTL 30 分钟，`Issue` 会作废旧令牌，`Consume` 读取即删除，`Discard` 清理待确认请求。
- 新增 `httpapi.Confirmation`：`ConfirmFlow` 注册表，统一 `Send`（签发令牌、生成 `/api/confirm/<kind>?token=` 链接、发信）与 `Confirm`（消费令牌、加载用户、执行 Apply、按 Target/SuccessKey/ErrorKey 回跳）。
- 删除 `internal/emailchange`，邮箱变更改为实现 `Flow()` + `apply()`；旧的 `/api/email/confirm` 由 `/api/confirm/email` 取代。
- 注销账号：`DELETE /api/account` 发确认邮件，`GET /api/confirm/account` 执行；先吊销会话与刷新令牌，再 `UserRepo.Purge` 级联删除 `users`、`oauth_accounts`、`user_groups`、`consents`、`client_user_grants`、`login_notices`，并丢弃待确认的邮箱变更。
- 管理员不能自助注销；SMTP 未配置时两处入口都不显示，`/api/me` 字段由 `email_editable` 改为 `mail_enabled`。
- 前端：用户中心新增注销区块与二次确认弹窗，登录页展示 `account_deleted` / `account_delete_error` 提示。
- 邮件链接指向 SPA `/confirm?kind=<kind>&token=` 确认页；`GET /api/confirm/<kind>` 只预览摘要不消费令牌，`POST /api/confirm/<kind>` 才执行并返回 `next` 供前端跳转。`ConfirmFlow` 提供 `Preview` / `Note` / `Danger`，页面文案由流程声明。
- 已知限制：上游登录会自动开户，注销后再次登录会得到空白账号。

## 最近功能提交安全/逻辑漏洞审查

- 审查范围：`b69754e` 至 `2eda434` 间安全相关功能（注销、邮箱别名、admin 改资料、用户组同步、微信扫码+验证码、学号校验、确认页提交、CSRF 防护）。
- 结论：无直接越权/接管账号的高危漏洞；管理员端点经 `RequireAdmin` 统一鉴权，会话 cookie `HttpOnly+SameSite=Lax` + `OriginGuard` 写请求比对方 Origin，确认流程改为 POST 防误执行，注销级联清理——整体安全设计到位。
- 发现的中低危问题（详见 `.workbuddy/security-review-2026-11-02.md`）：
  1. 【中】扫码登录确认后 `PollQRLogin` 不再校验 `bindHash`（`qr.go` 第180-186行），确认后1分钟窗口内持 challenge `id` 即可领会话，违背"防借他人二维码种会话"意图。
  2. 【中低】`PatchUser` 允许管理员降级/禁用自己或最后一个管理员，存在锁死风险。
  3. 【低】`DeleteGroup` 未禁止删除 `is_upstream` 组（与 `PatchGroup` 不一致），再同步会重建新 id 致组-客户端授权错位。
  4. 【低】`OriginGuard` 在无 Origin/Referer 时放行写请求；学号长度未校验；`user.Name` 进邮件正文未清洗。
- 建议优先修复 #1 与 #2。
