### 登录与 OIDC

- `internal/auth`：本地 Argon2id 校验优先；本地不匹配才回访上游，覆盖上游改密与首次登录。`Throttle` 限制 15 分钟内 5 次上游验证。
- `internal/oidc`：授权码 + PKCE、RS256 签发、`/.well-known/openid-configuration`、`/oidc/jwks|authorize|token|userinfo`。授权码存 Redis 且 `GETDEL` 一次性消费。scope 决定 claims，`profile` 带 `name`/`preferred_username`/`belong_class`，`email` 带 `email`/`email_verified`。
- `internal/httpapi`：`/api/login|logout|me`、`/login` 临时 HTML 登录页（React 上线后替换）、`/api/admin/*` 用户与用户组接口。
- `cmd/relayctl`：`client create|list|delete`、`user promote`。

### 授权准入链路

`/oidc/authorize` 现在依次检查：会话 → 用户组 → `oauth_clients.required_bindings`（缺绑定跳 `/?bind=<provider>&next=<authorize>`）→ `consents` 表里是否已覆盖所申请的 scope（未覆盖跳 `/consent?req=<id>`）→ PKCE → 发码。

- 待确认的授权请求存在 Redis（`oidc.Pending`，10 分钟），确认页只凭不透明 id 取用，避免伪造参数。
- `consents` 表按 (user_id, client_id) 唯一，授予时按 scope 合并。
- 绑定层 `internal/binding` 只依赖标准 OAuth2 授权码流程，provider 全部来自配置，新增来源不用改代码。`id_field`/`name_field` 指定对方 userinfo 里的账号标识与展示名。
- 绑定回调走 `GET /bindings/:provider/callback`，身份来自 Redis 里的 state，不依赖 cookie。
- **绑定完成后必须回到原授权请求**：`/` 的 `next` 参数在绑定成功（`?bound=`）时自动跳回，否则第三方应用会一直挂在等待状态。

## 关键结论

- **`des.js` 不是标准 DES**：`generateKeys` 把 PC1 表按转置取位，K1 得 `1B02EFA6E5F6`，标准 DES 为 `1B02EFFC7072`。上游服务端与之匹配，因此不能用 `crypto/des`，必须逐位复刻。已用 Node 跑参考值逐条比对通过。
- 该实现依赖全局变量 `i/j/k`，移植时不能按标准 DES 简化。
- 实测 2026-10-30：登录成功，`newmy` 的 `MOBILE` 返回的是**学号本身**（11 位），不是手机号。
- 参考项目 `G:\Project\Course-Bullying-in-GZHU\` 的密码字段是 UTF-8 十六进制编码。
- gorm 把 `OAuthClient` 拆成 `o_auth_clients`，三个 OAuth 模型都需显式 `TableName()`。
- 迁移已在临时内嵌 Postgres 上验证通过：`profile_data` 为 `jsonb`，时间列为 `timestamptz`，两组联合索引符合 PLAN。生产库由用户提供后再跑。

## profile_data 读取报 Scan 错误

`/api/me` 与 userinfo 每次取 `belong_class` 都打 `converting driver.Value type []uint8 ... to a uint8`。根因是 `AccountRepo.ProfileData` 用 `Pluck("profile_data", &raw)`：gorm 把 `*[]byte` 当成切片目标，按元素类型 `uint8` 逐行 Scan，于是 `[]byte` 落到 `*uint8` 上失败。`Pluck` 只适合 `*[]string`、`*[]uint64` 这类（仓库里其它 Pluck 都是这种，没问题）。

改为 `Select("profile_data") + Take(&model.OAuthAccount{})`，`ErrRecordNotFound` 返回 `nil, nil`，保持「无快照返回空」的旧语义。已提交 `d02ff42`。

另：日志里 `GET "/"` 404、`GET " /background.webp"` 200 与当前代码不符，实测 `web.Handler()` 对 `/`、`/login` 都返回 200 index.html；那条 404 大概率来自重建前启动的旧进程，重启即可。

## 登录失败被误判为上游不可用

上游 CAS 登录失败时返回的页面：状态 200、标题 `Unified Identity Authentication`、**含 `name="lt"` 但不含 `name="password"`**，提示文案在 `<span id="errormsghide">` 里，形如「连续登录失败5次，账号将被锁定5分钟，剩余次数3」。原实现只看 `name="password"` 判断失败，命中不了就落到「未进入融合门户」→ 502。

现在按提示节点分类：凭据错误（401）、账号锁定（429，用「锁定」且不带「剩余次数」区分）、要求验证码（502）。登录失败会打日志带上具体原因。门户 `getPIThree` 缺 `MOBILE` 时错误里带上顶层字段名，便于定位上游结构变化。

## 登录验证码（极验第四代）

需求是「单个 IP 登录失败一次，之后一天内都要验证；成功一次提前放开」。

- `internal/captcha`：极验 v4 二次校验，POST `https://gcaptcha4.geetest.com/validate?captcha_id=...`，表单带 `lot_number`/`captcha_output`/`pass_token`/`gen_time`/`sign_token`，`sign_token = HMAC-SHA256(captcha_key, lot_number)` 的十六进制。响应 `status` 与 `result` 同时为 `success` 才算通过；网络异常或非 200 归 `ErrUnavailable`，前端提示「验证服务不可用」。
- `internal/auth/captcha.go`：`CaptchaGuard` 用 Redis 键 `relay:captcha:<ip>` 记标记，`Flag` 时刷新 24h 过期时间；`Clear` 在登录成功时删除。
- `internal/httpapi/captcha.go`：`CaptchaPolicy` 把 guard 与 geetest 包在一起，`site == nil` 即未启用，所有方法都做了 nil 判定，main 里不需要分支。
- 只在 `ErrInvalidCredentials` 时打标记。上游锁定、上游不可用这些不算「密码错」，不打标记。
- `GET /api/public/config` 多了 `captcha: {enabled, captcha_id, required}`，`required` 按请求 IP 现算；`POST /api/login` 的错误响应带 `captcha_required`，前端据此立刻拉起验证，不用刷新。
- 前端 `web/src/lib/geetest.ts` 懒加载 `https://static.geetest.com/v4/gt4.js`，`product: "bind"` 不占布局：点击登录时 `showCaptcha()`，`onSuccess` 里取 `getValidate()` 再提交。验证失败后 `reset()`，避免复用旧流水号。
- `server.trusted_proxies`：gin 默认信任所有 `X-Forwarded-For`，按 IP 的标记会被随意伪造的请求头绕过。默认只信本机（`127.0.0.1`/`::1`），反向代理不在本机时要显式加进去，写成 `[]` 则一律用连接地址。
